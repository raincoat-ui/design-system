# RFC 0007: Tabs

- Status: proposed
- Kind: component
- Proposed: 2026-11-24
- Decided:

## Summary

Adds Tabs: a row of labels that switches between panels of related content in one view, such as
"Details", "Reviews", and "Shipping" on a product. It adds a color role for marking the selected
item in a set. Tabs are for content within a screen; moving between an app's main sections is
navigation, which follows in 1.x.

## Problem

Apps split long screens into panels and build their own tab rows. A hand-built row usually gets
one of three things wrong: arrow keys do not move between tabs, a screen reader is not told which
tab is selected or how many there are, or a translated label pushes the row past the edge of a
phone with no way to reach the last tab. Each platform has a different native expectation, and
SwiftUI has no in-view tabs at all: its `TabView` is app navigation and its segmented picker is
for choosing a value.

There is also no token for the mark of a selected item. `color.accent.default` fails 3:1 on
paper in the base (raincoat yellow is 1.48:1 on white), and a state mark has to reach 3:1.

## Proposal

### Anatomy

| Part      | Notes                                                                                                 |
| --------- | ----------------------------------------------------------------------------------------------------- |
| Tab list  | A row of tabs over a 1px hairline across the full width. It scrolls sideways when the tabs do not fit |
| Tab       | A label, with an optional leading icon. A tab with only an icon must be given an accessible name      |
| Indicator | A 2px bar under the selected tab, on top of the hairline                                              |
| Panel     | The content of the selected tab. Only the selected tab's panel is shown                               |

### Behaviour

- **One look, one size.** Tabs are `size.control.md` tall, which density makes 44 or 36px. No
  contained or vertical variant in v1.
- **Labels stay on one line,** in `type.label.md`, and are never truncated. Every tab uses the
  same weight, so selecting a tab does not change its width.
- **Overflow scrolls.** When the tabs do not fit, the list scrolls sideways. Moving focus to a tab
  scrolls it into view. On the web, a pointer that cannot scroll sideways gets previous and next
  buttons at the ends of the list; they are hidden from assistive technology and not in the Tab
  order, because the arrow keys already reach every tab.
- **No disabled tabs.** A tab that leads nowhere is hidden instead.
- **Selection** is controlled by the app or left to the component, as with other inputs.

| State         | Appearance                                                                          |
| ------------- | ----------------------------------------------------------------------------------- |
| Rest          | Label in `color.fg.muted`                                                           |
| Hover         | Label in `color.fg.default`, fill `color.control.hover`. Only with a pointer        |
| Focus-visible | The focus ring, drawn inside the tab's edge, so the scrolling list does not clip it |
| Pressed       | Label in `color.fg.default`, fill `color.control.pressed`                           |
| Selected      | Label in `color.fg.default`, and the indicator                                      |

### Tokens

A new semantic token, overridable by themes:

| Token                   | Holds                                                                                               | Light         | Dark          | Light HC      | Dark HC       | Contrast      |
| ----------------------- | --------------------------------------------------------------------------------------------------- | ------------- | ------------- | ------------- | ------------- | ------------- |
| `color.border.selected` | The mark of the selected item in a set: the selected tab now; the selected segment and radio in 1.x | `neutral.900` | `neutral.100` | `neutral.900` | `neutral.100` | 3:1 (graphic) |

It is checked against `color.bg.canvas`, `color.bg.surface`, `color.bg.subtle`, and
`color.bg.raised`. The base draws it in ink: a 2px ink rule under the selected tab, like the
rule that opens a section in the documentation. A brand theme can point it at its accent, as
long as the accent reaches 3:1; the base's yellow cannot.

Component tokens, `tokens/component/tabs.tokens.json`:

| Token                                 | Value                                               |
| ------------------------------------- | --------------------------------------------------- |
| `tabs.height`                         | `size.control.md`                                   |
| `tabs.padding-inline`                 | `space.4`                                           |
| `tabs.gap`                            | `space.2`, between icon and label                   |
| `tabs.label`                          | `type.label.md`                                     |
| `tabs.icon-size`                      | `size.icon.md`                                      |
| `tabs.fg.default`                     | `color.fg.muted`                                    |
| `tabs.fg.selected`, `tabs.fg.hover`   | `color.fg.default`                                  |
| `tabs.bg.hover`, `tabs.bg.pressed`    | `color.control.hover`, `color.control.pressed`      |
| `tabs.indicator.color`                | `color.border.selected`                             |
| `tabs.indicator.width`                | `border-width.thick`                                |
| `tabs.divider.color`, `.width`        | `color.border.default`, `border-width.thin`         |
| `tabs.focus-ring.width`, `.color`     | `border-width.focus`, `color.border.focus`          |
| `tabs.target-minimum`                 | `size.target.minimum`                               |
| `tabs.transition.duration`, `.easing` | `motion.duration.fast`, `motion.easing.interactive` |

`color.fg.muted` adds `color.control.hover` to the backgrounds it declares, as RFC 0005 also
needs. The label on the pressed fill is always `color.fg.default`, which already declares it.

Usage rules that will go into the guidelines:

- Use tabs for two to seven panels of related content that people do not need to compare side by
  side. For more, or for content people compare, use headings on one screen.
- Keep labels to one or two words, in sentence case, and do not repeat the screen's title in
  them.
- Do not use tabs to step through a process. Each tab must make sense on its own.
- Do not put tabs inside tabs.

Compose, Android, and Material Web documentation, because m3.material.io shows nothing without
JavaScript. Fluent 2 (web) and GitLab Pajamas were also read and appear below where they differ.

Where the systems disagree, and which way Raincoat goes:

- **Selection on focus.** Cloudscape and Spectrum select a tab when the arrow keys reach it;
  Fluent and Material Web wait for Enter or Space; Carbon offers both. Raincoat selects on focus
  on the web, which is quicker and what the WAI-ARIA Authoring Practices recommend when panels
  show at once. A tab whose panel loads slowly can wait for Enter or Space instead.
- **Overflow.** Carbon, Material, and Cloudscape scroll; Spectrum turns the row into a picker;
  Fluent uses an overflow menu. Raincoat scrolls: a picker and a menu are components v1 does not
  have, and a scrolling row looks the same on every platform.
- **Long labels.** Pajamas truncates with a tooltip and Compose's samples cut off after two
  lines; Carbon never truncates horizontal tabs. Raincoat never truncates. Translated labels
  scroll with the rest of the row.
- **Disabled tabs.** Carbon and Spectrum allow them; Cloudscape says to hide the tab instead.
  Raincoat follows Cloudscape. A disabled tab cannot say why it is disabled, the problem the
  Button guidelines describe.
- **Selected state.** Carbon uses `aria-selected`; Fluent's usage page names `aria-current`.
  Raincoat uses `aria-selected`, the attribute the `tab` role defines.

## Accessibility

| Requirement                                                                                                         | How it is tested                                                                                               |
| ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Roles: tab list, tabs with selected state and position, panels named by their tab                                   | Web: accessibility tree and axe. iOS: UI test of traits. Android: semantics test of the tab role and selection |
| Web keyboard: Left and Right move and select, wrapping at the ends; Home and End; Tab leaves the list for the panel | Playwright keyboard tests, left-to-right and right-to-left                                                     |
| Native keyboard: focus moves between tabs as the platform moves it; Enter or Space selects                          | Android key events; iOS Full Keyboard Access UI test                                                           |
| A panel with nothing focusable can take focus itself, so its content can be reached                                 | Web keyboard test                                                                                              |
| The indicator reaches 3:1, and the focus ring 3:1, against the background                                           | Token contrast check                                                                                           |
| Every tab's touch area is at least the minimum target                                                               | Target-size tests on each platform                                                                             |
| Reduced motion: color changes are immediate                                                                         | Snapshot with the reduced-motion setting                                                                       |

The selected tab is told apart by the indicator and by its label color, so it does not depend on
color alone: the indicator is a shape.

## Internationalization

- **Right-to-left.** The first tab is on the right, the list scrolls from the right, and Left and
  Right swap: Left moves to the next tab.
- **Long and expanded text.** Labels stay on one line and the row scrolls. Snapshots in the
  expanded pseudo-locale on a phone-sized screen show the row scrolled to its last tab.
- **Vietnamese and CJK** snapshots show a row in each locale. The tab height leaves room for
  stacked diacritics at line height 1.4.

## Platform notes

- **Web.** shadcn/ui's `tabs` source, adapted, on Radix Tabs, which handles roles, arrow keys, and
  direction. Panels that are not selected are not rendered unless the app asks to keep them.
- **iOS.** `RaincoatTabs`. SwiftUI has no in-view tabs, so it is a scrolling row of buttons. Each
  tab carries the selected trait when selected, and the row is marked as a tab bar for VoiceOver,
  so it reads the role and the position, such as "2 of 4". The simulator test checks what
  VoiceOver is given.
- **Android.** `RaincoatTabs` on Compose Foundation: the row is a selectable group and each tab is
  `selectable` with the tab role, which TalkBack reads with its selected state.
- **Selection on focus is web only.** On iOS and Android a hardware keyboard moves focus the way
  the platform does, and Enter or Space selects, as for any other control.

## Migration

None. This is a new component.

## Alternatives considered

- **A yellow indicator in the base.** The base's signal color marks where you are in the docs'
  sidebar, but as a 2px bar on paper it is 1.48:1, under the 3:1 a state mark needs. A brand
  accent that reaches 3:1 can be used through `color.border.selected`.
- **Equal-width tabs that fill the row.** Material and Pajamas offer them. With translated
  labels they stop fitting, and the component would then have to switch to scrolling, a second
  behaviour to test. They can come in 1.x.
- **Contained and vertical tabs.** More variants than v1 needs; vertical tabs are mostly a desktop
  pattern.
- **Count badges.** A Badge component does not exist yet. A count can be part of the label until
  it does.
- **SwiftUI's segmented picker on iOS.** Native, but it is for choosing a value, has a fixed
  look the theme cannot reach, and does not scroll when translated labels overflow.
