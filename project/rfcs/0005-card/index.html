RFC 0005: Card

  • Status: accepted
  • Kind: component
  • Proposed: 2026-11-24
  • Decided: 2026-11-24

Summary

Section titled “Summary”

Adds Card: a surface that groups content about one subject, such as an order, a contact, or an article, and that can lead somewhere as a whole. It adds a role for surfaces that sit above the page and a shadow for them, so that a theme can lift its cards while the base stays flat. It is for any app that lists things people choose between.

Problem

Section titled “Problem”

Apps show collections of similar things: orders, products, saved places. Each app draws its own box with its own padding, outline, and corners, and each solves the same accessibility problem differently: how to make the whole box open the item without hiding the buttons inside it, and without a screen reader reading every word of the box as the name of a link.

There is also no way for a theme to say how raised surfaces look. ADR 0010 lets a theme set “shadow style”, but no shadow token exists, so a brand that lifts its cards on a shadow cannot. Dialogs, sheets, and toasts (RFCs 0006 and 0008) need the same.

Proposal

Section titled “Proposal”

Anatomy

Section titled “Anatomy”
Part Required Notes
Container Yes The surface. Its outline, fill, and shadow come from the theme
Media No An image at the top, edge to edge, its top corners following the card’s. Its text alternative is the app’s
Title Yes A Heading (RFC 0003), heading-sm by default, at the level the page needs
Body No Any content: Text, a list of facts, a status
Footer No Actions, as Buttons, at the end of the card

Behaviour

Section titled “Behaviour”

A card is either static or interactive:

  • Static (the default) is a container. It can hold links and buttons.
  • Interactive leads somewhere or does one thing when any part of it is activated. It is a link (it has a destination) or a button (it has an action). An interactive card holds no other controls. A card that needs several actions is static, and its title can be a link.
State (interactive only) Appearance
Rest As a static card
Hover The outline steps to color.border.strong. Only where there is a pointer
Focus-visible The focus ring around the whole card, offset 2px
Pressed The fill steps to color.control.hover and the outline to strong

There is no disabled or selected card in v1. A selectable card needs the Checkbox (1.x); a card that cannot be opened should not look as if it could.

No variants and no sizes. One look, set by the theme, keeps every card in an app alike. A card fills the width it is given; the grid or list around it is the app’s.

Tokens

Section titled “Tokens”

New semantic tokens, overridable by themes:

Token Type Holds Base value, in every mode
color.bg.raised color Surfaces above the page: cards, dialogs, sheets, toasts The same as color.bg.canvas (neutral.0, neutral.950, neutral.0, neutral.1000)
shadow.raised shadow The shadow of a card shadow.none, a new primitive: one transparent layer with no offset, blur, or spread
  • The base stays flat. Its raised surface is the page’s own paper, separated by a hairline; the Standards Manual rule is “ruled, not raised”. A theme that lifts its surfaces sets color.bg.raised lighter than the canvas in dark mode, as elevation is usually shown there, and gives shadow.raised a value.
  • Contrast. Every text and graphic role that declares color.bg.canvas as a background also declares color.bg.raised, so a theme’s raised color is checked against all of them. color.fg.muted also declares color.control.hover, the pressed fill.
  • Shadows on every platform. The CSS build already writes shadow tokens. The Swift and Kotlin builds gain them: a SwiftUI shadow modifier per layer, and Compose’s drop shadow modifier, not its elevation, which cannot take a color or offset. A transparent shadow draws nothing.

Component tokens, tokens/component/card.tokens.json:

Token Value
card.radius radius.lg
card.padding space.4
card.gap space.3, between the parts
card.bg.default color.bg.raised
card.bg.pressed color.control.hover
card.border.width border-width.thin
card.border.default color.border.default. Overridable: a theme that wants filled cards with no outline points it at its fill
card.border.hover color.border.strong
card.shadow shadow.raised
card.focus-ring.width, .offset, .color border-width.focus, border-width.thick, color.border.focus
card.transition.duration, .easing motion.duration.fast, motion.easing.interactive

card.border.default is the first component token on the allowlist ADR 0010 provides for. A semantic role for it would be used by cards alone.

Usage rules that will go into the guidelines:

  • Put a collection of cards in a list, so a screen reader says how many there are.
  • Give every card a title, even when the media seems to say it all.
  • Make a card interactive only when the whole card leads to one place. If it needs a button, keep it static and make the title the link.
  • Let titles wrap. Shorten a description with max-lines (RFC 0003) only when the full text is one tap away.

Prior art

Section titled “Prior art”

Read from each system’s public documentation on 2026-11-24. Material and AWS Cloudscape were also read and appear below where they differ.

Question IBM Carbon (Tile) Adobe Spectrum Fluent 2 (web) GitLab Pajamas Raincoat
Parts (anatomy) A container with text; “Carbon does not have a card pattern” Container, optional checkbox, preview, title, metadata, footer; typed cards for assets, users, products Preview, header, footer; every slot optional Container, optional header, body, optional footer Container, optional media, title, optional body and footer
Variants and sizes Base, clickable, selectable, expandable; no sizes Four variants, five sizes, three densities Four appearances, three sizes, horizontal or vertical None; needing to change the padding means a card may be the wrong component None. One look, set by the theme
States Hover, focus, disabled; selected for selectable tiles Disabled, selected, skeleton loading; focus indicator at least 3:1 Hover and focus hint at selection; selected; disabled Loading Hover, focus, and pressed on interactive cards
Keyboard behaviour A clickable tile is one Tab stop, activated with Enter, and “cannot contain separate internal CTAs” Tab between cards; arrows move inside a card; Enter opens; Space selects focusMode chooses whether focus enters the card; Escape leaves Not read An interactive card is one Tab stop and holds no other controls
Screen-reader role, name, and announcements Interactive tiles take aria-label or aria-labelledby A card with href is a link role="group" by default; the title is a heading at the level the context needs No landmark meaning; heading level fits the page; collections as lists No role of its own; the title is a heading; an interactive card is named by its title alone
Right-to-left and long-text behaviour Not read Layout and metadata mirror; titles truncate in fixed-height grids and wrap in others Not read Not read Mirrors; titles wrap; cards grow with their content

Where the systems disagree, and which way Raincoat goes:

  • Controls inside an interactive card. Carbon forbids them, and Cloudscape says not to make a whole card clickable when it holds other controls. Spectrum lets a footer button take the click instead, and Fluent manages focus inside the card. Raincoat follows Carbon and Cloudscape: one card, one action. Nested controls need a focus model of their own, and the three platforms each handle a button inside a button differently.
  • Variants. Material and Fluent offer filled, outlined, and elevated cards; Pajamas offers none. Raincoat offers none: a theme decides how every card looks, so cards in one app cannot disagree.
  • Role. Fluent gives a card role="group"; Pajamas says it has no landmark meaning and puts collections in lists. Raincoat gives it no role and asks for a list.
  • Interaction feedback. Material changes elevation on hover and press; Carbon changes layer and border colors. Raincoat changes the outline and fill, which shows in a flat theme too.
  • Long titles. Only Spectrum says, and it truncates in fixed-height grids. Raincoat has no fixed heights, so titles always wrap.

Internationalization

Section titled “Internationalization”
  • Right-to-left. Every part aligns to the start edge, and footer actions sit at the end, on the left. Media does not flip; it is a picture, not a direction.
  • Long and expanded text. The title and body wrap; the card grows. Snapshots in the expanded pseudo-locale check that a card in a grid row grows rather than clips.
  • Vietnamese and CJK snapshots show a card with a two-line title in each locale.

Platform notes

Section titled “Platform notes”
  • Web. shadcn/ui’s card source, adapted. An interactive card’s title holds the real link or button, and a pseudo-element stretches its target over the card, so the accessible name is the title alone and text in the card can still be selected. The card shows the focus ring when its link has keyboard focus (:has(:focus-visible)), which every supported browser has.
  • iOS. RaincoatCard. An interactive card is a Button or NavigationLink with a card style, combining its children for VoiceOver so it is read as one element, title first.
  • Android. RaincoatCard on Compose Foundation. An interactive card is clickable with the button role and merged semantics. Compose has no link role, so a card that navigates is a button there, as a navigation row in a list is.

Migration

Section titled “Migration”

None. This is a new component. The token contrast checker gains one background to check, and the base’s values pass it, since color.bg.raised equals the canvas.

Alternatives considered

Section titled “Alternatives considered”
  • Filled, outlined, and elevated variants. More ways for cards in one app to disagree, and the theme can already make all of them filled or elevated.
  • Letting an interactive card hold buttons. The behaviour differs on every platform, and a screen reader reads the card and the button inside it as one control or as two depending on the platform. One action per card is predictable.
  • A semantic outline role for raised surfaces. Only cards need an outline a theme may remove; dialogs and sheets keep theirs, separated by a scrim. A component token is the smaller change.
  • No shadow tokens until a theme asks. ADR 0010 already promises themes a shadow style, and adding the token later would mean a minor release of every package for every theme.
