3.3

Input

A text field with its label, an optional description, and an error message.

Spec version 1.0.0, proposed in RFC 0004. The size and type types used by every platform’s implementation are generated from this spec.

Implemented in React (Input in @raincoat-ui/react), SwiftUI (RaincoatInput and RaincoatTextFieldStyle in Raincoat), and Compose (RaincoatInput in io.github.raincoat-ui:ui). The parity matrix shows every component on every platform.

About the renditions

The panels under “In every color mode” are static renditions, not the component: they take no text. They are styled only with the custom properties of the generated theme stylesheet, and each panel selects its mode with a data-theme attribute.

Properties

Section titled “Properties”
Property Values Default Description
size sm, md, lg md The height and text size of the field, the same heights as the Button’s.
type text, email, password, search, tel, url text What the field holds. It chooses the keyboard on touch screens and what autofill offers. A multi-line field holds text.
multiline true, false false Takes several lines. The field starts as many lines tall as its rows, 3 unless the app gives another number, and grows with its content.
required true, false false Tells assistive technology that the field must be filled in, where the platform has that state. The visible marking is the app’s text.
invalid true, false false The value is not accepted. The field shows its error message, which it must have.
disabled true, false false Makes the field unavailable. It cannot be focused. Prefer read-only when the value still matters.
read-only true, false false The value can be focused, selected, and copied, but not changed.

Size

Section titled “Size”
Value Use
sm For dense layouts such as toolbars and tables. Its text is 14px.
md The default size.
lg For prominent fields, such as the one field of a step.

Type

Section titled “Type”
Value Use
text Any text.
email An email address. It stays left-to-right in a right-to-left layout.
password A password. What is typed is not shown.
search A search query.
tel A phone number. It stays left-to-right in a right-to-left layout.
url A web address. It stays left-to-right in a right-to-left layout.

Content

Section titled “Content”
Content Description Required
Label What the field is for, in sentence case, above the field. It is the field’s name for assistive technology. It can be visually hidden when the purpose is plain, as in a search bar. Yes
Description Help that is read before typing, between the label and the field, such as the rule a value must follow. No
Error What to do to make the value acceptable, below the field. It is shown only while the field is invalid, and does not replace the description. When invalid
Placeholder An example of the format, shown while the field is empty, such as “name@example.com”. Never instructions, and never the label. No
Value The text in the field, typed by the person or given by the app. No
Leading icon An icon at the start of the field. Decorative. No

States

Section titled “States”
State Description
Rest The control fill, and a 1px outline in the control outline color.
Hover No change. The text cursor is the cue.
Focus The field has focus. On the web and Android the focus ring is shown whenever it does, since a field has focus only to be typed in. On iOS the system’s indicator and the caret.
Invalid The outline is in the danger color, and the error message is shown below the field. The message is the cue that does not depend on color.
Disabled The disabled fill, outline, and text, as on the Button.
Read only A subtle fill and a hairline outline, so that it reads as a value rather than a place to type.

Accessibility

Section titled “Accessibility”
Requirement Detail
Role textbox
Name The label, even when it is visually hidden.
Description Reaches assistive technology with the field. On the web the field is described by the description and then the error message. On iOS the description is the field’s accessibility hint; on Android it is part of the field’s semantics, read after its name.
Invalid Exposed as the field’s state: aria-invalid on the web and the error semantics on Android, which carry the message. iOS has no such state: the error message follows the label in the field’s accessibility label, as a loading Button says “In progress”. Errors are not announced as they appear: on submit, focus moves to the first field in error, which then reads its label, its state, and its message.
Required The required state on the web. iOS and Android have none; the label marks the fields that are optional, for everyone.
Disabled Not focusable and not editable. Exempt from contrast requirements.
Read only Focusable and selectable, and stays in the Tab order. Not editable.
Focus A ring at least 2px wide with 3:1 contrast against the surface behind the field. On the web and on Android the field draws it from the focus ring tokens whenever it has focus. On iOS the system draws its own indicator, which follows the person’s Full Keyboard Access settings, and the caret shows where typing goes.
Target size The area that takes touches is at least 44pt on iOS, 48dp on Android, and 44px on a touch screen on the web, whatever the field’s visible height. The field’s layout size is its visible size: around a smaller field the touch area reaches past the outline without taking room.
Contrast The outline has 3:1 against the surface behind the field, in error too. The label, the description, the error, the value, and the placeholder have 4.5:1, and 7:1 in high-contrast modes.

Keyboard

Section titled “Keyboard”
Keys Action
Tab Moves focus to and from the field. A disabled field is skipped; a read-only field is not.
Enter In a one-line field, submits the form, as the platform does. Never while an input method is composing: Enter that commits a composition does not submit. In a multi-line field, starts a new line.

Internationalization

Section titled “Internationalization”
Concern Behavior
Right to left Label, description, and error align to the start edge, and the leading icon sits on the right. Email, phone, and web address fields stay left-to-right, because their content is.
Long text Label, description, and error wrap and are never truncated. A long value scrolls inside a one-line field and wraps in a multi-line one.
Input methods Vietnamese (Telex, VNI) and CJK input methods compose a character before committing it. The field never replaces the value, changes its error state, or submits during composition, and Enter that commits a composition does not submit the form.
Scripts Line height 1.4 for labels and 1.5 for values clears stacked Vietnamese diacritics. CJK text uses system fonts.
Character limit None in v1. HTML counts length in UTF-16 code units, so a decomposed Vietnamese word counts as more characters than it shows.

Motion

Section titled “Motion”
Concern Behavior
Transitions None. Outline and fill change at once.

Guidelines

Section titled “Guidelines”

When to use

Section titled “When to use”

Use an input wherever people type: a name, an email address, a search, a message. For a choice from a fixed list, use a control made for choosing.

Use one line for a short value and multiline for text that can run to sentences, such as a comment. A multi-line field grows with what is typed.

Writing the label

Section titled “Writing the label”
  • Say what the field is for, in a few words, in sentence case: “Email address”, “Message”.
  • Do not end with a colon or a full stop.
  • Keep the label even when it is visually hidden, as in a search bar. It is still the field’s name for assistive technology.
  • Mark the fields that are optional, in the label: “Phone (optional)”. Most fields in a form are required, so marking the few that are not says less. Set required on the others, so that assistive technology says so where the platform can.

Description and placeholder

Section titled “Description and placeholder”
  • Put what someone needs before typing in the description: the rule the value must follow, or where it will be used. It stays visible above an on-screen keyboard.
  • Use the placeholder only for an example of the format, such as “name@example.com”. It disappears as soon as someone types, so it can never hold instructions or replace the label.

Errors

Section titled “Errors”
  • Check a field when the form is submitted, and move focus to the first field in error. After that, check a field as it changes, so that its error clears as soon as it is fixed.
  • Do not show an error while someone is typing into a field for the first time.
  • Say what to do, not what went wrong: “Enter an email address, like name@example.com”, not “Invalid input”.
  • Every invalid field has a message. The red outline is not enough on its own.
  • The error does not replace the description. Write it so the two read well together.

Sizes

Section titled “Sizes”
Size Use it for
sm Dense layouts on a desktop, such as a filter above a table
md Most forms
lg A prominent field, such as the one field of a sign-in step

A field and a button of the same size are the same height, so they line up in a row.

On the web, use md or lg on touch layouts: Safari on iPhone zooms into a field whose text is smaller than 16px when it takes focus, and sm uses 14px text.

Disabled and read-only

Section titled “Disabled and read-only”
  • Prefer read-only when the value still matters: a read-only field can be focused, selected, and copied, and assistive technology reads it.
  • A disabled field cannot be focused and cannot say why it is disabled. Explain nearby what is needed to enable it.

Spacing

Section titled “Spacing”

A field takes the room it shows. A field shorter than the minimum touch target still takes touches across that minimum, so its touch area reaches a few pixels past its top and bottom edges. Leave at least 8px (space.2) between a small field and the next control.

Do and don’t

Section titled “Do and don’t”
Do Don’t
Put the label above the field Put the label inside the field as its placeholder
Say how to fix an error: “Enter a date, like 31/12/2026” Say only that something is wrong: “Invalid value”
Mark optional fields: “Company (optional)” Mark every required field with an asterisk
Let a long label or error wrap Truncate a label or an error with an ellipsis
Use the email, phone, and web address types Use a text field for an email address
